### 测试资源保全与执行证据

Java 测试目录中的 `.ql` 脚本是行为契约的一部分，不能只保留同名 Rust 测试。
本轮将原始资源按相对路径镜像到
`crates/qlexpress/tests/fixtures/java-testsuite/`，并由
`verification/verify_java_testsuite_fixtures.py` 校验路径和内容：**228/228**
匹配（仅容许尾随换行符规范化）。

- `alignment_suite` 直接执行全部 **151** 个不依赖 Java 宿主类型的原脚本；
- `alignment_java_fixture_replay` 以显式 `NativeRegistry` 测试宿主执行全部
  **77** 个依赖 Java 宿主类型的原脚本；
- 两个测试目标分别为 **157 passed** 和 **30 passed**。后者的 30 个 Rust
  测试按 fixture 组聚合，覆盖的脚本数为 77，而非把 30 误报为 77。

这证明测试输入文件没有在迁移中丢失，并提供了可执行回放；它仍不能替代对
全部公开方法、边界行为和真实业务宿主的逐项契约验证。

当前 Java/Rust 实时差分为 **295/295**：除脚本执行外，包含 41 个直接
`NumberMath` 门面调用和 74 个具体数值域方法调用，显式构造 Java
`Byte/Short/Integer/Long/Float/Double/BigInteger/BigDecimal`，比较类型化
结果、NaN/Infinity 以及异常类别与原因；另有 41 项覆盖 `BaseBinaryOperator`
的运算、比较、集合包含、LIKE、移位和错误语义，以及 45 个直接
`OperatorManager` 注册、替换、查找、别名、优先级、未知词素 NPE 与适配器用例，以及 2 个
`DelegateQContext` 直接场景覆盖其 19 个构造/公开方法的运行时委托、符号、
函数表、共享栈、作用域身份与状态变化、全局关闭异常；1 个
`FixedSizeStack`/`Parameters` 直接场景覆盖 10 个方法、栈顺序、显式/越界
null、零长度 pop 及旧参数窗口被后续 push 覆盖的副作用；1 个 runtime_core
场景覆盖 `QRuntime`/`QvmRuntime`/`QContext` 的 11 个方法、对象身份及附件双向写穿；
1 个 `ExceptionTable` 场景覆盖其 3 个构造/公开方法、声明顺序、父类 catch、null 与 finally。
该直接 oracle 是语义证据；覆盖率仍只用于发现 Rust 未触达分支。

未知操作符 `precedence` 的 Java NPE/Rust None 差异已按 Java 当前实现修复，
并迁入正式差分语料；`OperatorManager` 对象和该方法已清除 `PARTIAL`。

`DelegateQContext` 差分发现 Rust 全局作用域 `closeScope()` 曾静默 no-op，
而 Java 委托 `QvmGlobalScope.getParent()` 会抛 `UnsupportedOperationException`；
该偏差已经修复并由正常/异常两个直接场景复验。此结论来自行为对比，不来自覆盖率。

`FixedSizeStack` 差分还发现 Rust `split_off` 曾让 `Parameters` 拥有弹出值，
导致其成为快照；Java 私有 `StackSwapParameters` 持有原 `Value[]`，后续
push 覆盖同一槽位时旧参数会读到新值。Rust 已改为共享定长槽位窗口，并逐次
比较覆盖后的 `[9,5,6]`、`[9,8,6]`、`[9,8,7]`。

`QRuntime` 对照发现 Java `attachment()` 返回的 Map 可写，而 Rust 原入口只有
不可变 `Ref`。Rust 现按借用规范增加 `attachment_mut()`，并验证外部 Map、
QvmRuntime 与 DelegateQContext 三方写入均立即由另外两方观察。

`ExceptionTable` 对照发现 Rust 默认查找曾只接受类型名相等或 `Object`，使 Java
`catch (Number)` 捕获 `Integer/Long`、`catch (RuntimeException)` 捕获子类的
`Class.isAssignableFrom` 语义丢失。Rust 已补齐内建继承关系；宿主自定义继承继续由
显式注册表判断入口承担，并由直接 oracle 复验首个匹配项和 finally 位置。

安全策略直接对照还发现 Rust 外观 `QLSecurityStrategy::Isolation.check` 曾返回
`false`，而 Java 接口工厂返回的 `StrategyIsolation.check` 会无条件抛出
`IllegalStateException`。Rust 现由 `check` 保留原始异常契约，由 `is_allowed`
单独承担注册表的安全布尔适配；同一差分场景复验四个工厂、null Member 和共享 Set。

`QLStringUtils` 对照发现 Rust 曾用 Unicode scalar 下标并把越界静默截断，偏离
Java `String#charAt` 的 UTF-16 下标和 `StringIndexOutOfBoundsException`。
Rust 现返回可保存未配对代理项的 `JavaString`，直接 oracle 已覆盖半个代理项、
补充字符、全部转义、未知转义、尾随反斜杠和越界区间。

## 2. 严格口径

审计遵循 `rust-java-migration` 与 `rust-java-migration-testing`：

1. 每个 Java 主对象必须有真实、独立的 Rust 对象文件。
2. 多层 Java 子包只保留最后一级目录；文件名使用可处理缩写边界的
   snake_case，例如 `QLParser` → `ql_parser.rs`。
3. 内部类、接口、枚举、record 和匿名类型也必须逐项记录处置方式。
4. 每个公开/受保护方法及其重载都必须记录 Rust 对应、参数、返回、错误、
   状态变化和副作用证据。
5. 严格状态只允许
   `MISSING / MISPLACED / STUB / PARTIAL / UNVERIFIED / IMPLEMENTED /
   DEPENDENCY_REUSED / PLATFORM_NA / RUST_EXTENSION`。
6. `UNVERIFIED` 不等于完成；只有契约级代码、测试和调用链证据完整时，
   才能进入 `IMPLEMENTED`。

## 5. 与旧文档结论的冲突

当前《对象级对照表》使用 `✅/🔶`，并声称 237/237 已完成；但该表：

- 没有使用严格状态，因此严格测试审计器无法解析任何当前对象行；
- 没有覆盖 136 个具名内部类型和 5 个匿名类型；
- 没有覆盖 1,814 个公开/受保护方法及重载；
- 接受 `qlparser.rs`、`qlambda.rs` 等旧缩写文件名；
- 接受完整多层目录，而仓库规范要求多层包只保留最后一级；
- 把同文件多个公开迁移对象计为完成。

因此，旧表只能作为“历史目标映射提示”，不能继续作为完成证明。
